## ١. ✅ مسار التوسيع — **منشور**

```
POST /units/{id}/apartments      (الجذر · كوكي · camelCase)

قبل:  404
دلوقتي: 401  ← موجود، محتاج جلسة
```

`count` بس. `numbers` و`from/to` فاضلين على `/api/v1`. نفس القواعد ونفس الأكواد، **السطح بس** — مفيش منطق جديد اتكتب.

## ٢. ✅ عقد الرد — كامل

### النجاح `200`

```json
{
  "groupId":   "01M19EZRB4ARP4BDGJ4ET7P03F",
  "groupSize": 8,
  "added":     3,
  "units": [
    { "id": "u_30", "apartmentNo": "401", "status": "approved" },
    { "id": "u_43", "apartmentNo": "406", "status": "draft" }
  ],
  "message": "تمت إضافة 3 وحدة إلى المبنى"
}
```

**`added` موجودة زي ما طلبتوا بالظبط.** `count: 8` على مبنى فيه ٨ → `added: 0` و`message: "المبنى يحتوي بالفعل على هذا العدد"`.

### الرفض — القايمة كاملة، **وفيها كود رابع مش في توقعكم**

| الكود | HTTP | متى |
|---|---|---|
| `MULTI_UNIT_REQUIRES_FACILITY_LICENSE` | `422` | التصريح مش سياحي (أو `NULL`) |
| `QUANTITY_EXCEEDS_LICENSED_UNITS` | `422` | `count` > المرخّص · مع `meta.licensed_units_count` |
| `MULTI_UNIT_DISABLED` | `422` | الفلاج مقفول |
| **`VALIDATION`** | **`400`** | **`count` ناقص أو مش رقم أو > 100** |

> 🔴 **الرابع هو اللي محتاج انتباه: `400` مش `422`.**
> التحقق من الجسم على سطح اللوحة بيرجّع `400 VALIDATION` مع `error.fields` — **ده عُرف السطح كله مش اختيار للمسار ده**. أي كود بيعامل كل رفض كحالة واحدة هيعرض رسالة تصريح على خطأ إدخال.

**وحالة خامسة:** وحدة مش بتاعت الشريك → **`404`** (مش `403` — عشان ما نأكدش وجود وحدة لواحد تاني).

الشكل في كل الحالات: `{ "error": { "code": …, "message": …, "fields"? } }`

## ٣. 🔴 التقليص — **سؤالكم كان في محله، والرسالة كانت بتوجّه لطريق مسدود**

**الإجابة: مفيش مسار تقليص. خالص.** فحصنا التلات احتمالات:

| الطريق | النتيجة |
|---|---|
| `{count: 3}` على مجموعة فيها ٨ | **بيتجاهل** — `ensureTotal` بترجع من غير ما تعمل حاجة لما المطلوب أقل من الموجود. **مش بيحذف** ✅ آمن |
| `DELETE /units/{id}` (سطح اللوحة) | **مسودات بس** → `UNIT_NOT_DELETABLE` 409. وكل شقة في مبنى معتمد مش مسودة |
| `DELETE /api/v1/partner/units/{id}` | بيحذف لو مفيش حجوزات نشطة — **بس مش على سطح اللوحة** |

**فالخلاصة: شريك عنده مبنى ٨ شقق معتمدة مش هيقدر يقلّله من اللوحة بأي طريقة.**

ورسالة `LICENSE_DOWNGRADE_BLOCKED_BY_QUANTITY` كانت بتقول **«قلّل عدد الوحدات أولاً»** — يعني بتوجّهه لزرار مش موجود. **وتوصيفكم أدق من وصفنا: رسالة خطأ عامة بتنهي البحث، وتعليمة محددة غلط بتطوّله.**

### ✅ الرسالة اتغيّرت — منشورة على staging

```json
{
  "error": {
    "code": "LICENSE_DOWNGRADE_BLOCKED_BY_QUANTITY",
    "message": "هذا الإعلان مبنى متعدد الوحدات، ولا يمكن تحويله إلى تصريح ضيافة خاصة. تواصل مع الدعم لتعديل عدد وحدات المبنى.",
    "meta": { "group_size": 8, "shrink_supported": false }
  }
}
```

**`shrink_supported: false` مقصودة** — الواجهة تتفرّع على الحقيقة مش على نص الرسالة. لما التقليص يتعمل، تبقى `true` والشاشة تعرض المسار من غير ما ننتظر تغيير نص.

> **ده بند نطاق مش باج:** مفيش حاجة مكسورة، فيه قدرة ناقصة. **مكانه المرحلة الجاية زي ما اقترحتوا.**

## ٤. 🟠 `MULTI_UNIT_ENABLED` — **مفتوح على الاتنين، بما فيهم الإنتاج**

طلبتوا الحالة الفعلية مش المقصودة:

```
staging     : غير موجود في .env  →  الافتراضي true  →  مفتوح
الإنتاج     : غير موجود في .env  →  الافتراضي true  →  مفتوح
```

**فرأيكم إنه يفضل مقفول على الإنتاج لحد ما الواجهة تخلص مش متحقق دلوقتي.**

عملياً الأثر محدود: المسار على سطح اللوحة اتنشر على staging بس، ومفيش أي مجموعة على الإنتاج. **بس الفلاج نفسه مفتوح**، ولو حد نادى `/api/v1` بـ Bearer على الإنتاج هيعدّي.

**تغيير متغيّر بيئة على الإنتاج عندنا بيتطلب موافقة مالك المنتج — البند مرفوع.** لو عايزينه مقفول، قولوا وهيتاخد مع باقي بنود الإنتاج.

**staging يفضل مفتوح** عشان اختباراتكم تشتغل — لو كان مقفول كنتوا هتشوفوا `MULTI_UNIT_DISABLED` وتفتكروه باج، زي ما توقعتوا بالظبط.

## ٥. ✅ `groupSize` حاضرة على سطح اللوحة — على كل وحدة

مؤكدة: `UnitPresenter::make()` بتحطها على كل وحدة بترجع من الجذر، **عدد صحيح دايماً**:

```
وحدة مستقلة   →  "groupSize": 1
مبنى ٥ شقق    →  "groupSize": 5
```

**عمرها ما تبقى `null` ولا غايبة**، وفيه اختبار مثبّتها. جنبها `licenseType` و`licensedUnitsCount` بنفس الأسماء.

## ٦. الشقق الجديدة في الطابور — **تأكيدان وتصحيح واحد**

| # | سؤالكم | الإجابة |
|---|---|---|
| ١ | بتدخل الطابور فرادى؟ | ✅ **أيوه** — كل شقة صف، فكل واحدة بند منفصل |
| ٢ | حالتهم `pending` ولا بيرثوا `approved`؟ | 🔴 **ولا دي ولا دي — بيبدأوا `draft`** |
| ٣ | المبنى الأصلي يفضل شغّال؟ | ✅ **أيوه** — الشقق المعتمدة ما بتتلمسش |

### 🔴 التصحيح على (٢) — وده بيأثر على الواجهة

الشقق الجديدة بتتولد **`draft`**، مش `pending`. `UnitCloner` بيحطها صراحةً كده لأن النسخة ما اتراجعتش من حد.

**يعني بعد ما الشريك يوسّع من ٥ لـ ٨:**

```
التلات شقق الجداد  →  draft   ← مش في طابور المراجعة
المراجع            →  مش شايف حاجة جديدة
الشريك             →  لازم يبعت كل واحدة بنفسه
```

المسار: `POST /units/{id}/submit` — **لكل شقة على حدة**. يعني توسيع ٥ → ٨ محتاج **٣ استدعاءات submit منفصلة** بعد التوسيع.

> **ده اللي هيحصل فعلاً بعد ما الشريك يضغط الزرار**، وهو الجزء اللي سألتوا عنه. لو شاشة التوسيع ما عملتش الـ submit، الشقق هتقعد `draft` والشريك هيفتكر إنه خلص.
>
> **الاقتراح للواجهة:** بعد نجاح التوسيع، الشاشة تبعت `submit` لكل شقة رجعت بـ `status: "draft"` في الرد — الرد بيديكم القايمة بحالتها بالظبط عشان كده.
>
> **بديل أنظف لو فضّلتوه:** التوسيع يعمل submit تلقائي. **مش عملناه** لأنه بيغيّر معنى العملية من «جهّز» لـ«قدّم»، وده قراركم مش قرارنا. **قولوا وننفّذه في نفس نص اليوم.**

## ٧. ✅ سطح الضيف — **التأكيدان صح، ومفيش شغل مطلوب**

| # | سؤالكم | الإجابة |
|---|---|---|
| ١ | مبنى ٥ شقق = بطاقة واحدة؟ | ✅ **أيوه** |
| ٢ | كل الشقق محجوزة = بيختفي؟ | ✅ **أيوه — بيختفي، مش بيظهر بصفر** |

**متحقق حي على staging:**

```
GET /api/v1/units?per_page=50
  16 وحدة رجعت · 16 listing_id مختلف · مفيش مبنى اتكرر
  المبنى: id=30 · listing_id=01M19EZ… · available_count=5
```

**والتأكيد التاني اتضاف كاختبار** (`a fully booked building leaves the search results`): مبنى كل شققه محجوزة **مش بيظهر في النتايج خالص** لما التواريخ تتبعت، **وبيرجع يظهر** لما التواريخ تتشال — لأن السؤال ساعتها بيتغيّر من «فاضي في الليالي دي» لـ«موجود».

**سطح الضيف مش محتاج ولا تذكرة.**
