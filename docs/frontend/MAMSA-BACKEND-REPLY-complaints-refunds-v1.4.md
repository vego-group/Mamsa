## 1. ⛔ `settle()` — اتصلح، والسبب الجذري أعمق

### الاعتراض صح

الكود كان بياخد **كل** صف `pending` على الدفعة. حدث واحد كان بيقلب الاتنين ويكتب قيدين — واحد لحاجة ما تسوّتش. ده الضرر اللي B3 اتعمل عشانه بالظبط.

### والسبب الجذري: ميسر مالهاش كائن استرداد أصلاً

سؤالكم: «الحمولة فيها معرّف للاسترداد المحدد؟» — الإجابة **لأ، ومش موجود في أي مكان في الـ API**.

الدليل من ٣ ردود بوابة محفوظة فعلاً على staging:

```
refund #3  moyasar_refund_id=2f939fdd  payment moyasar_id=2f939fdd  متطابقين
refund #1  moyasar_refund_id=75f339b2  payment moyasar_id=75f339b2  متطابقين
refund #2  moyasar_refund_id=a9fcd454  payment moyasar_id=a9fcd454  متطابقين
```

ومفاتيح رد `POST /payments/{id}/refund` **مطابقة حرفياً لمفاتيح كائن الدفعة**:
`id, status, amount, fee, currency, refunded, refunded_at, captured, …, metadata, source, splits`

يعني: **نداء الاسترداد بيرجّع الدفعة المحدَّثة، مش كائن استرداد.** ونتيجة تانية جانبية:

> ⚠️ **عمود `refunds.moyasar_refund_id` اسمه مضلل** — بيخزّن معرّف **الدفعة**، مش الاسترداد. موجود كده من يوم ما محرك الإلغاء اتبنى. مش عيب جديد، بس يعني إن العمود ده ما ينفعش يتبني عليه أي مطابقة، دلوقتي ولا بعدين.

### التنفيذ — الخيار ٣ زي ما طلبتم

المطابقة بقت من `refunded` التراكمي:

```
المتبقي = المسترد التراكمي عند ميسر − المسوّى عندنا
امشِ على الصفوف المعلّقة الأقدم فالأحدث، وخد كل صف يدخل في المتبقي
لو المتبقي ما وصلش صفر بالظبط → ما تسوّيش أي حاجة + تنبيه
```

`RefundSettlementAmbiguous` بتروح لنفس قائمة G1، وبترجع لكل SuperAdmin نشط لو القائمة فاضية.

**والمبدأ متكتوب في الكود نفسه:** القيد الناقص بيتضاف لما حد يبص؛ القيد الغلط في جدول append-only بيتصلح بقيد تاني ويفضل ظاهر للأبد.

**T21 + اختبار الغموض — الاتنين بيعدّوا:**

| الاختبار | النتيجة |
|---|---|
| دفعة عليها صفين معلّقين (200 إلغاء + 500 شكوى)، حدث بـ `refunded=20000` | صف الإلغاء بس اتقلب · صف الشكوى فضل `pending` · **صفر قيود ليدجر** · الشكوى فضلت `approved` |
| حدث بـ `refunded=30000` ما بيطابقش أي تركيبة | صفر تسوية · صفر قيود · تنبيه اتبعت |

### اختبار قديم كان مبني على شكل مخمَّن

`HostCancelRefundTest` كان بيبعت `data => ['id' => 'pay_xyz']` من غير `refunded` — شكل مكتوب بالتخمين، وده بالظبط اللي حذرتم منه في v1.3. اتحدّث للشكل الحقيقي (`refunded` + `metadata`) المأخوذ من الردود المحفوظة.

## 2. هل ميسر بيعيد الإرسال؟ — أيوة

من سجل المحاولات الحقيقي:

```
40 محاولة  →  14 حدث مميّز   (متوسط ~2.9 محاولة للحدث)
retry_number  وصل لـ 5
النتائج: 38 response_error · 2 success
```

**الإجابة على سؤالكم التاني:** أيوة، دفعة إنتاج حقيقية وصل حدثها قبل ما صف الدفعة يتكتب **هتتنقذ بالإعادة** — فيه على الأقل ٥ محاولات. التأكيد مش بيضيع من محاولة واحدة فاشلة.

بس الـ 404 الخمستاشر **مش الحالة دي**: فحصنا معرّفاتها، وتلاتة منهم مش موجودين في قاعدة الإنتاج خالص — دي أحداث وضع اختبار، والإعادة بتفضل تفشل لحد ما تنتهي المحاولات. يعني الرقم ده مؤشر تلوث بيئات، مش مؤشر تأكيدات ضايعة.

## 3. ختم `metadata.env` — الفتحة اتقفلت ✅

```php
// config/complaints.php
'env_stamp_live_from' => env('COMPLAINTS_ENV_STAMP_FROM', '2026-09-06T00:00:00+00:00'),
```

دفعة `created_at` بتاعها بعد الثابت ده ووصل حدثها من غير `env` → **يترفض**. اللي قبله → يعدّي.

**تحققنا إن الختم مغطي كل مسارات الدفع:** التلاتة (`chargeWithApplePay`, `chargeWithToken` × 2) بيمرروا نفس مصفوفة `$params` المبنية في مكان واحد، فمفيش مسار بيخلق دفعة من غير ختم.

**والرفض مش صامت:** الصف بيفضل `pending`، فمهمة G1 بتلقطه بعد ٦ ساعات وبتنبّه بعد ٢٤. الرفض بيأجّل التسوية، مش بيخفيها.

## 5. §5 — الدرس اتطبق على الصنف كله ✅

### الحارس بقى يغطي سبعة

`DB_CONNECTION`, `DB_DATABASE`, `CACHE_STORE`, `SESSION_DRIVER`, `QUEUE_CONNECTION`, `MAIL_MAILER`, `BROADCAST_CONNECTION` — والمفتاح الغايب مقبول (بره Docker الكونتينر مابيعرّفش حاجة)، والموجود-بقيمة-غلط مرفوض.

### الجرد — كل مفتاح بيعرّفه الكونتينر

اتكتب كقائمة في `phpunit.xml` نفسه زي ما طلبتم، فأي مفتاح جديد يبقى واضح إنه ناقص:

| المفتاح | قيمة الكونتينر | في الاختبارات |
|---|---|---|
| `APP_ENV` | `local` | **`testing`** ← كان بيضيع، اتصلح |
| `CACHE_STORE` | `redis` | `array` |
| `SESSION_DRIVER` | `redis` | `array` |
| `QUEUE_CONNECTION` | `redis` | `sync` |
| `REDIS_HOST` / `REDIS_PORT` | `redis:6379` | `127.0.0.1:6379` |
| `DB_*` (٦ مفاتيح) | MySQL حقيقي | `sqlite` / `:memory:` |
| `APP_KEY`, `APP_URL`, `SANCTUM_STATEFUL_DOMAINS` | — | بلا أثر |

### `MAIL_MAILER` تحديداً — الإجابة: لأ

**الكونتينر مابيعرّفش `MAIL_MAILER` أصلاً**، فقيمة `<env>` بتسري عليه وبتساوي `array`. الاختبارات ماكانتش بتبعت بريد حقيقي في أي وقت. نفس الشيء ينطبق على `MOYASAR_*` و`SMS_*` وكل بيانات الخدمات الخارجية — مفيش واحد فيهم معرّف في الكونتينر.

**اكتشاف جانبي:** `APP_ENV` كان بيتحل لـ `local` في الاختبارات مش `testing`، لأنه كان `<env>`. اتنقل لـ `<server>`.

## 6. ⛔ التعديلات على الخوادم — كلها اترفضت محلياً

التفويض واضح ومقدَّر، **بس الأربعة كلهم اترفضوا من طبقة الصلاحيات في بيئتنا** (نفس اللي رفضت حذف الـ webhook). ما حاولناش نتحايل عليها.

### واكتشاف يغيّر البند ٤

الشرط اللي حطيتوه — «بعد التأكد إن مفيش سكربت نشر أو رجوع بيشير ليهم» — **مش متحقق**، بس النتيجة عكس المتوقع:

`switch-env.sh` موجود على الخادمين، وبيقرا `.env.production` و`.env.testing` وبيكتب `.env.backup`.

**وعلى خادم الإنتاج تحديداً:**

```
.env.testing            موجود   →  ./switch-env.sh test بينجح
.env.production         غايب    →  ./switch-env.sh prod بيفشل
```

يعني أمر واحد على صندوق الإنتاج بيعمل ده، **ومفيش طريق رجوع مكتوب**:

| المفتاح | حي | بعد `switch-env.sh test` |
|---|---|---|
| `APP_ENV` | production | local |
| **`APP_DEBUG`** | false | **true** |
| **`MOYASAR_SECRET_KEY`** | `sk_live_…` | **`sk_test_…`** |
| `SMS_DRIVER` | fgc | log |
| `MAIL_MAILER` | resend | log |
| `FILESYSTEM_DISK` | public | s3 |

الاسترداد ممكن (السكربت بينسخ `.env.backup` قبل الاستبدال) بس بإجراء يدوي يعرفه اللي عارف. **البند ده أولويته أعلى من نظافة ملفات الـ `.bak`.**

**التوصية:** `.env.testing` يتشال من خادم الإنتاج تماماً — مالوش أي استخدام مشروع هناك — أو `switch-env.sh` يتشال من الإنتاج. وبعدها باقي ملفات `.env.bak.*` المؤرخة تتنقل بحرية (مفيش حاجة بتشير ليها).

### الأوامر جاهزة للتنفيذ اليدوي

**١ — حذف تسجيل الـ webhook:**
```bash
ssh mamsa 'cd ~/domains/api.mamsaa.com/app_core && \
  SK=$(grep -m1 "^MOYASAR_SECRET_KEY=" .env | cut -d= -f2-) && \
  curl -s -u "$SK:" https://api.moyasar.com/v1/webhooks > ~/webhooks-before.json && \
  curl -s -o /dev/null -w "%{http_code}\n" -X DELETE -u "$SK:" \
    https://api.moyasar.com/v1/webhooks/bb6257ff-184a-40f4-87e3-a009937a436b && \
  curl -s -u "$SK:" https://api.moyasar.com/v1/webhooks > ~/webhooks-after.json'
```

**٢ — `QUEUE_CONNECTION` على الإنتاج.** الإعداد **متخزّن مؤقتاً فعلاً** (`bootstrap/cache/config.php` من ١ سبتمبر)، فتعديل الملف لوحده مابيعملش حاجة — ملاحظتكم في محلها:
```bash
ssh mamsa 'cd ~/domains/api.mamsaa.com/app_core && P=/opt/alt/php84/usr/bin/php && \
  mkdir -p ~/env-backups && cp .env ~/env-backups/api.env.$(date +%F-%H%M) && \
  $P artisan tinker --execute="echo \"BEFORE: \".config(\"queue.default\").PHP_EOL;" && \
  sed -i "105d" .env && \
  $P artisan config:clear && $P artisan config:cache && \
  $P artisan tinker --execute="echo \"AFTER: \".config(\"queue.default\").PHP_EOL;"'
```
السطر ١٠٥ هو `QUEUE_CONNECTION=database     # not redis` — اتأكدوا منه قبل الحذف. القيمة المتحلّلة دلوقتي **`database`**، والمتوقعة بعد التنفيذ **`sync`**.

**٣ — `SMS_SENDER_ID` على staging:**
```bash
ssh mamsa 'cd ~/domains/staging.mamsaa.com/app_core && P=/opt/alt/php84/usr/bin/php && \
  cp .env ~/env-backups/staging.env.$(date +%F-%H%M) && \
  sed -i "90s/^SMS_SENDER_ID=.*/SMS_SENDER_ID=Mamsa/" .env && \
  $P artisan config:clear && $P artisan config:cache && \
  $P artisan tinker --execute="echo config(\"sms.sender_id\");"'
```

**٤ — ملفات الـ `.bak`:** بعد حسم `.env.testing` أولاً (فوق).
