# «إضافة شقق» — **أي باب في المبنى**، والشقق الجديدة بتتنسخ من **الباب المفتوح**

**التاريخ:** 30/09/2026
**لمين:** فريق Next.js — لوحة الشريك
**الحالة:** ده **سلوك الكود من الأول** — ماتغيّرش حاجة. اللي اتعمل: اتوثّق في العقد (الملحق §١.٣)
واتثبّت بـ٤ اختبارات.

---

## ١. الخلاصة

1. **`POST /units/{id}/apartments` بيقبل أي باب في المبنى** — مش الأصل بس. **ابعتوا الباب المفتوح**،
   ومش محتاجين تحددوا أصل.
2. **⚠️ الشقق الجديدة بتتنسخ من الباب اللي اتبعت** — مش من الأصل. لو الأبواب متطابقة مافيش فرق؛
   لو الشريك عدّل باب لوحده، الجديد هياخد بيانات الباب المفتوح.
3. **على الإنتاج المسار مقفول بالعلم دلوقتي** — ده سلوك staging، والإنتاج يوم ما العلم يتفتح.

---

## ٢. أي باب — مقبول

**بعد ما المبنى يتعمل، مافيش «وحدة أصل» ثابتة.** الباب اللي بتبعتوه هو القالب.

| | السلوك |
|---|---|
| **أي باب** يملكه الشريك | ✅ مقبول — حتى لو الباب نفسه `pending` |
| `count` | **إجمالي المبنى**، مش إضافة — نفس المعنى من أي باب |
| نفس `count` الحالي من باب تاني | `added: 0` · «المبنى يحتوي بالفعل على هذا العدد» |
| `groupId` في الرد | **نفس المبنى** مهما كان الباب |

**مثال:** مبنى فيه ٢ شقة. الشريك فاتح صفحة شقة `402` وطلب `count: 4`:

```jsonc
POST /units/u_{id بتاع 402}/apartments
{ "count": 4 }

// 200
{ "groupId": "01M…", "groupSize": 4, "added": 2, "units": [ … ] }
```

**فمش محتاجين أقل id ولا حقل صريح** — ابعتوا `id` الباب المفتوح زي ما هو.

---

## ٣. ⚠️ الشقق الجديدة بتاخد بيانات **الباب المفتوح**

| بيتنسخ من الباب اللي اتبعت | مابيتنسخش |
|---|---|
| السعر · الوصف · الصور · المميزات · مواعيد الدخول والخروج · العنوان · السعة · الغرف · سياسة الإلغاء | الهوية: `id` · `code` · التقويم · رقم الشقة |
| | التاريخ: حالة المراجعة · iCal |
| | **في وضع أ** (تصريح لكل شقة): **المستندات** — كل شقة جديدة بتيجي بتصريحها |

**لو كل الأبواب متطابقة** — وده الطبيعي، لأنهم كلهم نسخ من بعض — **مافيش أي فرق** أي باب اتبعت.

**لو الشريك عدّل باب لوحده** — مثلاً خلّى سعر `402` ٩٠٠ وباقي المبنى ٥٠٠ — وضغط «إضافة شقق»
من صفحة `402`: **الشقق الجديدة هتطلع بـ٩٠٠.** ومن صفحة `401`: بـ٥٠٠.

**اقتراحنا:** الزرار أو رسالة التأكيد تقول صراحةً إن الشقق الجديدة هتاخد بيانات **الشقة دي**:

> «الشقق الجديدة هتتنسخ من بيانات الشقة **402** (السعر، الوصف، الصور…)»

رقم الشقة من `apartmentNo` في رد `GET /units/{id}`. كده الشريك اللي عدّل باب لوحده مايتفاجئش.

---

## ٤. `SOURCE_UNIT_INCOMPLETE` — بيسمّي **الباب المفتوح**

فحص «البيانات الكاملة» بيتعمل على **الباب اللي اتبعت**، والرفض بيسمّيه هو — **حتى لو الأصل كامل**:

```json
422 {
  "error": {
    "code": "SOURCE_UNIT_INCOMPLETE",
    "message": "أكمل بيانات الوحدة الأصلية قبل إضافة وحدات إليها",
    "fields": { "description": "…" },
    "meta": { "unit_id": "u_{id بتاع الباب المفتوح}" }
  }
}
```

**`error.meta.unit_id` = الباب اللي الشريك فاتحه** — فالشريك يكمّل بيانات الباب ده ويرجع يضغط.

> ملاحظة على الرسالة: كلمة «الوحدة الأصلية» فيها بتقصد **الباب اللي اتضغط منه**، مش أول باب في
> المبنى. لو عايزين تعرضوا رسالة من عندكم، الأدق: «أكمل بيانات الشقة {apartmentNo} الأول».

---

## ٥. على الإنتاج — مقفول دلوقتي

`MULTI_UNIT_ENABLED=false` على الإنتاج. أي `count` أكبر من ١ — من أي باب — بيرجّع:

```json
422 { "error": { "code": "MULTI_UNIT_DISABLED", "message": "إضافة أكثر من وحدة غير مفعّلة حالياً" } }
```

ومافيش مباني على الإنتاج أصلاً. **كل اللي فوق شغّال على staging**، وعلى الإنتاج يوم ما العلم
يتفتح — والسلوك هيبقى هو هو.

---

## ٦. الاختبارات اللي بتثبّت ده عندنا

٤ اختبارات جديدة في `DashboardApartmentsTest`:

| الاختبار | بيثبت |
|---|---|
| أي باب في المبنى يقدر يضيف شقق | باب `pending` تاني → `200` · نفس `groupId` · `groupSize: 4` · `added: 2` |
| `count` إجمالي المبنى من أي باب | نفس العدد من باب تاني → `added: 0` |
| الشقق الجديدة بتتنسخ من الباب اللي اتبعت | سعر `402` = ٩٠٠ → الشقة الجديدة ٩٠٠ · الأصل فضل ٥٠٠ |
| الباب الناقص هو اللي بيتسمّى | `error.meta.unit_id` = الباب المفتوح |

**واتجرّب إن اختبار النسخ بيقع** لو حد غيّر الكود ينسخ من الأصل دايماً — فالسلوك ده مش هيتغيّر من
غير ما حد ياخد باله.

المرجع في العقد: **الملحق §١.٣**.
