# رد الباك اند — `GET /me/complaints` بيرجّع 500

**التاريخ:** 07/09/2026
**المرجع:** `MAMSA-BUG-me-complaints-500-staging.md`
**الحالة:** ✅ **اتصلح ومتحقق منه حيّاً على staging** — والتحقيق كشف باج تاني أخطر

البلاغ كان ممتاز. **تمييزكم بالزمن هو اللي حسم الموضوع:** ٢٧٣ ملي ثانية مقابل ١٠ ثواني هو الفرق بين خطأ عندنا وانقطاع شبكة عندكم، وبدونه كنا هندوّر في المكان الغلط. والملاحظة إن `401`/`403` كانوا هيبانوا لو المشكلة مصادقة وفّرت فرضية كاملة.

## ٢. السبب — مش أي واحد من الأربع احتمالات

الاحتمالات الأربعة كانت منطقية كلها، والسبب كان حاجة تانية خالص. السطر من `laravel.log`:

```
SQLSTATE[42S22]: Unknown column 'code' in 'SELECT'
select `id`, `code`, `unit_id` from `bookings` where `bookings`.`id` in (83)
{"userId":4}
```

### `bookings` مافيهاش عمود `code` — ولا مرة كان فيه

فحصنا التلات بيئات:

```
الإنتاج   NO code column
staging   NO code column
التطوير   NO code column
```

ومفيش أي migration بتضيفه. الكود بتاعنا كان بيعمل:

```php
->with(['booking:id,code,unit_id', …])
```

يعني بيحط `code` في جملة `SELECT` صراحةً — وMySQL بيرفض العمود اللي مش موجود.

**وده بيفسر ليه القراءة العادية ما كانتش بتفشل:** `$booking->code` بيرجّع `null` بهدوء (خاصية مش موجودة)، وباقي الكود في المشروع بيتعامل مع ده أصلاً بـ `$booking->code ?: $booking->id`. المشكلة تظهر **بس** لما تسمّي العمود في `SELECT`.

### ⚠️ وكان بيأثر على التلات أسطح مش واحد

نفس الغلط كان في:

| الملف | السطح |
|---|---|
| `Dashboard/ComplaintController` | لوحة الشريك ← **اللي بلّغتوا عنه** |
| `AdminPanel/ComplaintsController` | **لوحة الأدمن** |
| `Api/V1/ComplaintController` | **تطبيق الضيف** |

لوحة الأدمن كانت هتضرب 500 على نفس النداء بجلسة حقيقية. ما ظهرش لأن الاختبار الوحيد اللي اتعمل عليها كان `401` من غير تسجيل دخول. **البلاغ بتاعكم منع باجين تانيين.**

### قيمة `bookingCode`

بقت `$booking->code ?: (string) $booking->id` — **نفس التعبير بالحرف** اللي `PartnerWalletService` بيكتب بيه `ref_code` في الليدجر.

ده مقصود: ربط سطر كشف الحساب بالشكوى عندكم بيعتمد على مطابقة السلسلتين. لو اتباعدوا، الربط هيقف في صمت.

## ٣. ⚠️ ليه ٥٢٦ اختبار ما مسكوش ده

السؤال ده أهم من الباج نفسه.

**الـ suite بيشتغل على SQLite، وSQLite مش بيرفض أسماء الأعمدة الغلط.** لارافيل بيقتبس المعرّفات بعلامات مزدوجة (`"code"`)، وSQLite عنده سلوك توافقي موثّق: **الاسم المقتبس بعلامتين اللي مايطابقش عمود بيتعامل كنص حرفي**، مش كخطأ.

قِسناها:

```
SQLITE:  select "code" from bookings  →  نجح، بلا خطأ
MYSQL:   select `code` from bookings  →  Unknown column 'code'
```

يعني `with('booking:id,code')` بيفضل أخضر على SQLite للأبد، وبيرجّع 500 على MySQL أول ما جلسة حقيقية تلمسه.

### الحارس اللي اتضاف

اختبار بيمسح جمل الـ eager load في الكونترولرات التلاتة، وبيتأكد إن كل عمود مسمّى فيها **موجود فعلاً في المخطط** عن طريق `Schema::hasColumn` — ودي مستقلة عن المحرك، فبتمسك الصنف اللي الاستعلام نفسه ما يقدرش يمسكه.

> **الخلاصة اللي تستاهل تتسجل:** الاختبارات على SQLite بتثبت المنطق، **مش** صحة أسماء الأعمدة. أي فحص للمخطط لازم يبقى صريح.

## ٤. 🔴 وباج تاني أخطر ظهر أثناء الإصلاح

بعد الإصلاح فشل اختبارين كانوا بيعدّوا من ساعات. **مكانش بسبب التعديل — كان التاريخ اتغيّر لـ ٧ سبتمبر.**

```php
Carbon::parse($booking->end_date, 'Asia/Riyadh')
```

`start_date` و`end_date` معرّفين `cast` كـ `date`، فبيوصلوا **ككائنات Carbon بتوقيت التطبيق (UTC)**. و`Carbon::parse()` **بيتجاهل معامل المنطقة الزمنية لما تديله Carbon بدل نص**:

```
تمرير Carbon :  2026-09-07T00:00:00+00:00
تمرير نص     :  2026-09-07T00:00:00+03:00
الفرق        :  ٣ ساعات
```

**يعني نافذة الشكوى كلها كانت بتتحسب بـ UTC مش بتوقيت الرياض:**

- الضيف كان يقدر يقدّم شكوى **بعد الموعد النهائي بـ ٣ ساعات**
- ومكانش يقدر يقدّم في **أول ٣ ساعات من يوم الوصول**

وده يخالف R4 صراحةً، والحد ده وعد لضيف واقف في السعودية.

### ليه ما ظهرش قبل كده

الاختلاف بين الحسابين بيظهر **بس** في نافذة ٣ ساعات بعد منتصف الليل بتوقيت الرياض. الاختبارات كانت بتبني تواريخها من `now()` الحقيقي، فكانت بتعدّي طول اليوم وتفشل في الساعات دي بس — والـ suite ما اتشغلش فيها قبل النهاردة.

### الإصلاح

```php
Carbon::parse(Carbon::parse($booking->start_date)->format('Y-m-d'), $tz)->startOfDay()
```

الاختزال لنص تاريخ الأول بيخلي معامل المنطقة يسري.

**والاختبارات بقت على ساعة مجمّدة** (`Carbon::setTestNow`) بدل الوقت الحقيقي، ومعاها اختبار حدود متثبّت **جوه نطاق الـ ٣ ساعات المتنازع عليه** — اتأكدنا إنه بيفشل على الكود القديم:

```
قبل الإصلاح:  ⨯  رجّع 201 والمفروض 422
بعد الإصلاح:  ✓  422 WINDOW_CLOSED · و 201 قبلها بـ ٩٠ دقيقة
```

## ملاحظة

البلاغ ده لقى تلات باجات مش واحد: الـ 500 اللي بلّغتوا عنه، ونفسه على سطحين تانيين، ونافذة زمنية غلطانة بـ ٣ ساعات ما كانتش هتتكشف غير لما ضيف حقيقي يقدّم شكوى في التوقيت الغلط.

**والزمن هو اللي بدأ كل ده.** لو البلاغ قال «بيرجّع 500» وبس، كان أول شك هيروح للشبكة — وهي فعلاً كانت بتفشل في نفس التشغيلة.
