## ١. نطاق التناقض — تصحيحكم مقبول

وصفنا كان «السجل بيقول تم الاسترداد والقرار رفض». **ووصفكم أدق:**

```
عند الرفض   →  SMS: «تمت مراجعة شكواك… لم يتم قبولها»
بعد ساعة    →  SMS + إيميل: «تم استرداد 500.00 ريال»
```

رسالتين متناقضتين لنفس الضيف، والفلوس راحت فعلاً، والشريك اتخصم **391.30** فعلاً.

فاللي كان بيتصلح مش «صف حالة غلط» — ده **قرار اتشال من السجل بينما أثره المالي اتنفذ بالكامل**، ومعاه رسالتان متضاربتان لطرف خارجي. الأولوية اللي أعطيناها كانت أقل من اللازم، والتصنيف بتاعكم هو الصح.

## ٢. حارس `settle()` — ✅ متنفّذ

ملاحظتكم صح تماماً: حطينا الحارس على **باب دخول** واحد وسبنا **المصرف** مفتوح. أي مسار جديد كان هيعيد فتح نفس الفجوة و`settle()` هتنفذها بصمت.

### التنفيذ — بالفصل اللي حددتوه

```php
if ($status === STATUS_APPROVED) {
    $complaint->update(['status' => STATUS_RESOLVED_REFUNDED]);   // الطريق الطبيعي
} elseif ($status !== STATUS_RESOLVED_REFUNDED) {
    $unexpectedStatus = $status;                                   // لا كتابة + تنبيه
}
```

**القيد المحاسبي بيتكتب في كل الحالات** — قبل الفحص ده وخارج نطاقه.

المنطق بالحرف زي ما كتبتوه، ومكتوب في الكود نفسه:

> القيد بيوصف **اللي حصل** — الفلوس اتحركت، والليدجر لازم يقولها مهما كانت حالة الشكوى.
> الحالة بتوصف **اللي اتقرر** — والكتابة فوق قرار مسجّل بتمسحه.
> منع الاتنين أسوأ من أي واحد فيهم: فلوس اتحركت ومفيش قيد بيقولها.

### استثناء واحد أضفناه

`resolved_refunded` **مش** بيولّد تنبيه. ده بيحصل لما مهمة المطابقة توصل بعد ما الـ webhook سوّى نفس الصف — كتابة نفس القيمة، بلا تناقض. التنبيه عليه كان هيدرّب الناس إنهم يتجاهلوا الإيميل ده، وساعتها التنبيه الحقيقي هيضيع وسط الضوضاء.

أي حالة تانية (`submitted`، `under_review`، `resolved_rejected`) → تنبيه `SettlementOnUnexpectedState` لنفس قائمة G1.

### T23 — واتأكد إنه بيفشل قبل الإصلاح

| | النتيجة |
|---|---|
| **بدون الحارس** | ⨯ «a recorded decision must not be overwritten by settlement» — الرفض اتكتب فوقه |
| **مع الحارس** | ✅ قيد ليدجر −391.30 مكتوب · الحالة فضلت `resolved_rejected` · تنبيه اتبعت |
| **المسار الطبيعي** | ✅ من `approved` → `resolved_refunded` · **وتنبيه ما اتبعتش** |

الاختبار التاني مقصود: من غيره، حارس بيولّد تنبيه على كل تسوية عادية كان هيعدّي.

**ملاحظة على الاختبار:** الحالة اتفرضت بـ `forceFill` لأن كل المسارات الطبيعية للوصول ليها بقت مقفولة — وده بالظبط الغرض من الحرّاس.

## ٣. مصفوفة الانتقالات — مضافة، وبأثر رجعي

اقتراحكم مقبول ومطبّق على الفيتشر دي دلوقتي مش الجاية — **§1.2 في الـ prompt**.

وملاحظتكم إن «مفيش مستند بيعرض كل الانتقالات مع بعض» هي التشخيص الصح لسبب التلات عيوب: الـ prompt كان بيوصف الحالات، والكود بيوصف كل endpoint، ومحدش كان بيوصف **التقاطع**.

العمود الأخير — `approved` + استرداد ماشي — فيه التلاتة كلهم:

| الفعل | من `approved` + استرداد ماشي |
|---|---|
| amend | ⛔ `canAmendApproval=false` · 409 |
| execute | ⛔ 409 `REFUND_IN_FLIGHT` |
| reject | ⛔ 409 `REFUND_IN_FLIGHT` |

وضفنا خانة سابعة مش فعل واجهة بس بتهم العرض: **تسوية على شكوى مش `approved`** → قيد بيتكتب، حالة ما بتتغيرش، تنبيه. يعني لو الشاشة عرضت شكوى `resolved_rejected` وعليها استرداد `succeeded`، **ده مش باج عرض** — دي حالة شاذة مسجّلة عن قصد وفيه حد اتبلّغ.
