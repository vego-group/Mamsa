# رد الباك اند — الرفض من `approved` ونطاق الحارس

**التاريخ:** 06/09/2026
**المرجع:** `MAMSA-BACKEND-QUESTIONS-2.md`
**الحالة:** الاتنين متنفذين · **519 اختبار، صفر فشل** · منشور على staging · الـ prompt بقى **v3**

أعتذر إن السؤال الأول فات من الجولة اللي فاتت. الإجابة كانت «أيوة» — بس فحصه كشف فجوة في الاتجاه التاني.

---

## ١. الرفض من `approved` — كان مسموح، وكانت ناقصة حارس

### الإجابة المباشرة: أيوة، كان مسموح

`reject()` كان بيرفض بس لو الحالة **محسومة** بالفعل:

```php
if (in_array($complaint->status, BookingComplaint::RESOLVED_STATUSES, true)) {
    $this->fail('CONFLICT', 'تم البت في هذه الشكوى بالفعل', 409);
}
```

يعني `submitted` و`under_review` و**`approved`** الثلاثة كانوا بيعدّوا. المسار اللي وصفتوه كان شغّال.

### بس مكانش فيه أي فحص للاسترداد الجاري — وده اللي كان ناقص

كان ينفع ترفض شكوى **واستردادها ماشي عند البوابة**. وبعدها بساعة، لما التسوية توصل:

```
settle()  →  complaint.status = 'resolved_refunded'
```

**بتكتب فوق `resolved_rejected`.** فالسجل النهائي بيقول «تم الاسترداد» بينما القرار المسجّل كان رفض، والرسالة اللي راحت للضيف كانت رفض. تناقض دائم في جدول مالي.

### الإصلاح — بشرطكم بالحرف

```php
public function canReject(): bool
{
    return ! in_array($this->status, self::RESOLVED_STATUSES, true)
        && ! $this->hasRefundInFlight();
}
```

و`canAmendApproval()` بقت بتستخدم **نفس** الدالة:

```php
public function canAmendApproval(): bool
{
    return $this->status === self::STATUS_APPROVED && ! $this->hasRefundInFlight();
}
```

قلتوا «بنفس شرط `canAmendApproval` بالظبط» — فخلّيناه **تعريف واحد مشترك** بدل شرطين متطابقين، عشان ما يفترقوش بعدين. `failed` مستبعد: ما رجّعش حاجة، فما يصحّش يجمّد الشكوى.

### الكود عند الرفض

```
HTTP 409  { "code": "REFUND_IN_FLIGHT",
            "message": "لا يمكن رفض الشكوى بعد بدء تنفيذ الاسترداد" }
```

نفس الكود المستخدم في التنفيذ، لأن السبب واحد: فيه فلوس ماشية. الواجهة اللي بتتعامل معاه في زر التنفيذ بتتعامل معاه هنا من غير شغل زيادة.

### تعديل على العقد

```diff
  complaint: {
    canAmendApproval: boolean
+   canReject: boolean          // ← يتحكم في إظهار زر الرفض
  }
```

**الـ prompt اتحدّث لـ v3** ومعاه جدول الأزرار: الرفض بقى ظاهر في `approved` كمان، مش في `under_review` بس.

### الاختبارات

| الاختبار | النتيجة |
|---|---|
| رفض بعد اعتماد مبلغ، بلا استرداد | ✅ يعدّي · الحالة `resolved_rejected` · صفر صفوف استرداد |
| رفض ومعاه صف `pending` | ✅ `409 REFUND_IN_FLIGHT` · الحالة تفضل `approved` |
| العقد بيعرض `canReject` | ✅ |

## ٢. نطاق الحارس — التعليق اتكتب، وتحليلكم اتأكد

مش طلب تغيير، زي ما قلتم. بس تأكدنا من الادعاء قبل ما نكتبه، والثلاث نقاط صحيحة:

```
CancelBookingAction.php:42       يرفض لو الحالة cancelled أو completed
HostCancelBookingAction.php:41   يشترط الحالة confirmed بالظبط
ComplaintController::store()     يشترط الحالة completed
```

فالمسارين فعلاً ما بيتقابلوش على نفس الحجز، وحارس على مستوى الشكوى كافي.

التعليق اتحط عند الحارس نفسه — مش في وثيقة — وبيقول الجزء المهم صراحةً:

> **قيد حالة الحجز ده حامل حِمل، مش تفصيلة.** لو حد بعدين سمح باسترداد إلغاء على حجز `completed`، أو بشكوى على حجز متلغي، المسارين هيتسابقوا على نفس السقف والحارسين مش هيشوفوا بعض. توسعة أي مجموعة حالات معناها إعادة النظر في ده — **قفل على مستوى الحجز** عند إنشاء الاسترداد، مش على مستوى الشكوى.

ومعاه أسماء الملفات والأسطر الثلاثة فوق، عشان اللي بيقرا يتحقق بنفسه بدل ما يصدّق تعليق.
