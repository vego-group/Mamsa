# صفحة الحجز بتفضل «جاري التحميل…» للأبد لما المستخدم مش مسجّل دخول

**الصفحة:** `https://www.mamsaa.com/my-reservations/{id}`
**التاريخ:** ٠١/٠٩/٢٠٢٦
**الجهة المسؤولة:** الفرونت (الـ API بيرد صح — التفاصيل تحت)

---

## المشكلة

فتح `/my-reservations/101` من غير تسجيل دخول → الصفحة بتفضل على **«جاري التحميل…»**
ومابتوصلش لأي حالة نهائية. لا رسالة خطأ، لا طلب تسجيل دخول، لا صفحة فاضية.

والكونسول بيقول السبب:

```
GET api.mamsaa.com/api/v1/bookings/101         → 401
GET api.mamsaa.com/api/v1/bookings/101/review  → 401
Uncaught (in promise) ApiError: Unauthenticated.   ×2
```

يعني الطلبين وقعوا، والـ rejection مامتمسكش، فالمكوّن فضل في حالة `loading`
اللي مافيش حاجة بتخرجه منها.

> **ملاحظة:** `seal.js — ERR_CONNECTION_TIMED_OUT` و `A listener indicated an
> asynchronous response…` في نفس الكونسول **مش من الموقع** — دول من إضافة
> متصفّح. مالهمش علاقة بالمشكلة، متضيّعوش وقت فيهم.

---

## ده مش عطل في الـ API

الـ 401 صح ومقصود: دي endpoints بتاعة ضيف مسجّل دخول، والطلب جه من غير توكن.

```bash
$ curl -H "Accept: application/json" https://api.mamsaa.com/api/v1/bookings/101
{"message":"Unauthenticated."}          HTTP 401

$ curl -H "Accept: application/json" https://api.mamsaa.com/api/v1/bookings/101/invoice
{"message":"Unauthenticated."}          HTTP 401
```

الـ body ثابت وواضح: `{"message":"Unauthenticated."}` مع 401. مافيش redirect،
ومافيش HTML — يعني الفرونت عنده كل اللي محتاجه عشان يفرّق.

**والـ API مش هيتغيّر هنا.** التوكن مايتحطّش في لينك، والصفحة المحمية لازم
تطلب تسجيل دخول زي أي صفحة محمية.

---

## ليه ده مستعجل دلوقتي ⚠️

إيميل تأكيد الحجز بقى فيه **زرار «عرض الفاتورة الضريبية»** بيوّدي على:

```
https://www.mamsaa.com/my-reservations/{id}
```

والضيف اللي بيفتح اللينك ده من الإيميل بتاعه **مسجّل خروج بحكم التعريف** —
إيميل بيتفتح على جهاز أو متصفّح تاني. يعني الحالة اللي الصفحة بتعلّق فيها
دلوقتي هي **أول حاجة هيشوفها** أول ضيف حقيقي.

اللينك جاهز من ناحيتنا ومتوقف على ده. **مش هننشره على production قبل ما
الصفحة تتعامل مع 401.**

## المطلوب

### ١) الأساس: امسك الـ 401 واطلب تسجيل الدخول

لما أي طلب يرجّع 401 على الصفحة دي:

1. اخرج من حالة `loading`
2. اعرض طلب تسجيل الدخول
3. **وبعد الدخول ارجع لنفس الصفحة** — `/my-reservations/{id}` بنفس الـ id

النقطة التالتة هي المهمة. لو الضيف دخل ولقى نفسه على الصفحة الرئيسية، هو جاي
من إيميل عشان فاتورة حجز معيّن وضاع منه.

> **ملاحظة على التنفيذ:** مالقيناش راوت `/login` على الموقع (`/login`،
> `/auth/login`، `/signin` كلهم 404)، فمفهوم إن الدخول modal. الآلية قراركم —
> بس لازم الرجوع للصفحة يشتغل مهما كانت.

### ٢) امسك الـ rejection على مستوى طبقة الـ API

`Uncaught (in promise)` معناها إن مافيش حاجة بتمسك أخطاء الـ fetch. حتى لو
اتظبطت الـ 401، أي خطأ تاني (شبكة، 500) هيسيب الصفحة معلّقة بنفس الشكل.
المفروض يبقى فيه مسك مركزي في الطبقة اللي بتنادي الـ API، مش في كل مكوّن.

### ٣) باقي الحالات اللي الصفحة لازم تعرفها

| الحالة | الرد | المفروض تعرض إيه |
|---|---|---|
| مش مسجّل دخول | `401` `{"message":"Unauthenticated."}` | اطلب تسجيل الدخول ثم ارجع |
| الحجز مش بتاعه | `403` `{"message":"غير مصرح"}` | «الحجز ده مش على حسابك» |
| حجز مش موجود | `404` | «الحجز غير موجود» |
| **مافيش تقييم** | `200` والـ **body = `null`** | مش خطأ — يعني لسه مافيش تقييم |
| فاتورة قبل الدفع | `409` `INVOICE_NOT_AVAILABLE` | «الفاتورة متاحة بعد إتمام الدفع» |

الصف الرابع بالذات: `/bookings/{id}/review` بيرجّع **`null` مع 200** لما مافيش
تقييم. لو الكود بيعامل الـ body الفاضي كخطأ، ده هيبوّظ صفحة حجز سليمة تمامًا.

## للاختبار

`101` **مش موجود على production** (مافيش أي حجز عليها لحد دلوقتي)، فحتى لو
سجّلت دخول هترجع `404` مش `200`. الـ 401 بيسبقها، عشان كده هي اللي ظهرت.

للاختبار الحقيقي استخدموا **staging**، وفيها حجوزات فعلية:

```
مسجّل خروج → لازم يطلب تسجيل دخول (مش تحميل لا نهائي)
مسجّل دخول بحساب تاني → 403
id مش موجود → 404
حجز مدفوع → الصفحة تعرض والفاتورة تفتح
```
