### 1.3 الباقي

## 2. سؤال ١ — مؤشر الوضع في الحمولة

### الإجابة المباشرة: مفيش حقل وضع

فحصنا كائن الدفعة المخزّن فعلاً من الإنتاج (`payments.moyasar_response` لدفعة حقيقية). المفاتيح كلها:

```
id, status, amount, fee, currency, refunded, refunded_at, captured, captured_at,
voided_at, description, amount_format, fee_format, refunded_format,
captured_format, invoice_id, ip, callback_url, created_at, updated_at,
metadata, source, splits
```

**مفيش `livemode` ولا `mode` ولا أي مكافئ.** وواجهة `GET /v1/webhooks/attempts` مابترجّعش جسم الطلب أصلاً، فمش مصدر للإجابة.

### بس فيه إجابة أحسن من «لأ»

فيه `metadata` — وده **حقلنا إحنا** وبيترجّع في الحمولة. فبدل ما نستسلم للقاعدة التشغيلية كحماية وحيدة، بقينا نختم البيئة على كل دفعة وقت إنشائها:

```php
'metadata' => ['payment_id' => …, 'booking_id' => …, 'env' => config('app.env')],
```

والمعالج بيرفض أي حدث ختمه مخالف لبيئته.

**الحارس بيقوى مع الوقت، مش بيشتغل فجأة:** أي دفعة اتاخدت قبل النهاردة مالهاش ختم، و`env` الغايبة **مش** بتتعامل كمخالفة — لأن رفضها كان هيعلّق استردادات حقيقية على حجوزات قائمة. يعني:

> **القاعدة التشغيلية بتاعتكم (ممنوع `moyasar_id` من الإنتاج على staging) لسه سارية ولازمة.** الختم بيغطي الجديد؛ القاعدة بتغطي القديم. الاتنين مطلوبين.

### T16 — الحماية اتبنت على الافتراض الأسوأ

مابنعتمدش على «المعالج التاني مش بيكتب». التسوية بقت:

```php
$settledIds = DB::transaction(function () use ($payment) {
    $pending = $payment->refunds()->where('status','pending')->lockForUpdate()->get();
    if ($pending->isEmpty()) return collect();
    Refund::whereIn('id', $pending->pluck('id'))->update(['status' => 'succeeded']);
    return $pending->pluck('id');
});
```

الصفوف بتتقفل وتتقلب **جوه ترانزاكشن واحدة**، والقيود بتتكتب **بس** للمعرّفات اللي النداء ده قلبها فعلاً. تسليمة تانية — سواء إعادة إرسال أو نفس الحدث من التسجيل التاني — بتستنى القفل، بعدين ما تلاقيش حاجة pending، وما بتسوّيش حاجة.

ده بيغطي الحالتين اللي طلبتوها: إعادة الإرسال، **و** التسجيلين.

## 4. تصحيح لكلامنا في v1.2 §5

قلنا في v1.2 إن الـ `-e` overrides «مابقتش مطلوبة». **ده كان صح للداتابيز بس، وغلط في العموم.**

نقلنا `DB_*` لـ `<server>` وسبنا `CACHE_STORE` و`SESSION_DRIVER` و`QUEUE_CONNECTION` في `<env>`. والكونتينر بيحطهم كلهم على **redis**، فبنفس أسبقية `$_SERVER` بالظبط اللي شخّصناها، الاختبارات كانت بتشتغل على **Redis حقيقي مشترك**.

الأثر: عدّادات الـ rate limiter كانت بتعيش بين الاختبارات **وبين التشغيلات**. تشغيل الـ suite الكامل كان بيدي ١٤ فشل في ٣ كلاسات غير مترابطة، كلها 429، وكانت بتفشل لوحدها كمان.

اتصلح: الستة كلهم بقوا `<server>`، والحارس في `TestCase` بقى يرفض التشغيل لو `CACHE_STORE` مش `array`.

```
قبل:  14 فشل، 495 نجاح
بعد:  0 فشل،  509 نجاح (2120 assertion)
```

**الدرس مش «فاتنا مفتاح».** الدرس إن نفس الخطأ اتكرر لأننا صلّحنا الحالة اللي وجعتنا بدل ما نصلّح الصنف كله. أي مفتاح بيعرّفه الكونتينر ولازم يتغيّر في الاختبارات لازم يبقى `<server>` — مش `<env>`.

## 5. عيبين ظهروا من الاختبارات

الاتنين حقيقيين، والاتنين اتكشفوا بالتشغيل مش بالمراجعة.

### T4 — مفتاح التكرار كان بيرجّع 409

التنفيذ الناجح بينقل الشكوى لـ `resolved_refunded`. فالطلب المعاد — النموذج المتبعت مرتين، العميل اللي عمل timeout وأعاد — كان بيتصادم مع فحص الحالة **قبل** ما يوصل لفحص التكرار، ويترفض بـ 409 لأنه ببساطة نجح قبل كده.

المواصفة §5.2 صريحة: مفتاح معاد يرجّع النتيجة الأصلية بـ 200. فحص التكرار اتنقل لأول الدالة، قبل فحص الحالة وقبل فحص المبلغ.

### T19 — `refunds.payment_id` عمود NOT NULL

حجز من غير صف دفع كان هيطلع انتهاك قيد على مستوى الداتابيز بدل ما يطلع رد مفهوم. بقى يترفض برسالة.
