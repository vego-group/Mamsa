# رد الباك اند — حارس التنفيذ المزدوج

**التاريخ:** 06/09/2026
**المرجع:** `MAMSA-BACKEND-QUESTIONS-double-execute-guard.md`
**الحالة:** 🔴 **العيب حقيقي — اتصلح واتنشر على staging** · 516 اختبار، صفر فشل

المسار اللي وصفتوه صح بالحرف، وكل خطوة فيه اتأكدت في الكود. **ده أخطر عيب اتكشف في السلسلة كلها**، ومكتشَف من قراءة آلة الحالة قبل ما يتكتب سطر واجهة واحد.

---

## السؤال ١ — هل كان بيرفض؟ **لأ. الحارس اتضاف.**

### المسار كان مفتوح بالكامل

كل خطوة في تحليلكم اتأكدت:

```
execute()  →  refunds.status = pending          ← الفلوس راحت للبوابة
              complaint.status = approved        ← لأن resolved_refunded بتتحط في settle() بس
              الشاشة لسه بتعرض زرار «تنفيذ»
```

وتنفيذ تاني بمفتاح **جديد** كان بيعدّي كل الفحوصات:

| الفحص | النتيجة |
|---|---|
| `idempotencyKey` مستخدم قبل كده؟ | ❌ لأ — مفتاح جديد |
| `complaint.status === approved`؟ | ✅ أيوة — لسه approved |
| `mayExecute(amount)`؟ | ✅ أيوة — نفس المبلغ المعتمد |
| `amount <= refundable`؟ | ✅ أيوة — **الحساب كان بيعد `succeeded` بس، فالـ 500 المعلّقة كانت خفية عنه** |

**النتيجة: صف استرداد تاني، نداء تاني للبوابة، وخصم تاني من الشريك.**

وملاحظتكم إن حماية الـ idempotency مش بتغطي الحالة دي **دقيقة**: هي بتمسك **نفس الطلب** مرتين، ودي طلب مختلف بعد دقائق بمفتاح مختلف.

### الإصلاح

**حارس داخل قفل صف الحجز** — عشان طلبين متزامنين يتسلسلوا والتاني يشوف الأول:

```php
$inFlight = Refund::where('complaint_id', $complaint->id)
    ->whereIn('status', [Refund::STATUS_PENDING, Refund::STATUS_SUCCEEDED])
    ->first();

if ($inFlight) { throw new RefundInFlightException($inFlight->id); }
```

### الكود اللي الواجهة تتعامل معاه

```
HTTP 409
{
  "code": "REFUND_IN_FLIGHT",
  "message": "يوجد استرداد قيد التنفيذ على هذه الشكوى بالفعل",
  "fields": { "refundId": "12" }
}
```

**كود مستقل عن `REFUND_FAILED` عن قصد.** ما فشلش حاجة — فيه استرداد ماشي. الشاشة المفروض تقول كده وتعطّل الزر، مش تعرض خطأ يغري بإعادة المحاولة. و`fields.refundId` بيدي الصف اللي تعرضوا حالته.

### الاختبار — واتأكد إنه بيفشل قبل الإصلاح

```
بدون الحارس:  التنفيذ التاني رجّع 200 وأنشأ صف استرداد تاني  ⨯
مع الحارس:    409 REFUND_IN_FLIGHT · صف واحد · صفر قيود ليدجر  ✓
```

الاختبار بيتأكد كمان إن الشكوى **بتفضل `approved`** بعد التنفيذ الأول — أي إنه بيثبت وجود الفتحة نفسها، مش بس إنها مقفولة.

## السؤال ٢ — كان بيطرح الناجحة بس. **اتغيّر.**

كان مقصوداً وقتها (R10: الصف المعلّق ممكن يفشل، والفاشل ما رجّعش حاجة) — **بس الحالة اللي كشفتوها بتثبت إنه غير كافٍ**. المعلّق مش «ممكن يفشل» وبس؛ هو كمان «فلوس البوابة قبلتها».

دلوقتي **`succeeded` + `pending` الاتنين محسوبين** في كل مكان بيتحسب فيه سقف: التنفيذ، الاعتماد، وتعديل الاعتماد. `failed` لسه مستبعد — ده ما رجّعش حاجة فعلاً.

### وأثر على العقد — أضيفوه عندكم

```diff
  booking: {
    alreadyRefundedHalalas: number    // مُسوّى فعلاً
+   pendingRefundHalalas:   number    // عند البوابة، لم يُسوَّ بعد
    maxRefundableHalalas:   number    // = gross − already − pending
  }
```

الرقمان منفصلان عن قصد: لو دمجناهم، الشاشة مش هتقدر تفسّر ليه السقف أقل من المبلغ المسترد الظاهر. **دفاع في العمق زي ما اقترحتم** — الحارس هو الحماية، والسقف هو الطبقة التانية.

### الـ pre-push hook — ✅ **ملاحظتكم صح، اتصلح**

كان في `.git/hooks` — نسخة واحدة، ولشخص واحد. اتنقل لـ `.githooks/` (متعمله commit، بيتفعّل بـ `git config core.hooksPath .githooks`) **ومعاه فحص CI على كل PR**:

```yaml
# .github/workflows/backend-tree-shape.yml
- name: The backend must sit at the repository root
  run: |
    if [ -d backend ]; then exit 1; fi
    for required in artisan composer.json app config routes; do
      [ -e "$required" ] || exit 1
    done
```

**الـ hook بقى راحة، والـ CI هو الحارس** — زي ما قلتم بالظبط. والفحص بيمسك الاتجاهين: فرع فيه `backend/`، وفرع ناقصه `artisan` في الجذر.
